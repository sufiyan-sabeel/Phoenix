Technical Architecture

A comprehensive breakdown of PHOENIX's internal subsystem architecture, execution pipeline, Android IPC bridge, and process isolation model.

01

High-Level Subsystem Architecture

PHOENIX is organized into four primary subsystems: the Core Runtime, the Provider Bridge, the Execution Engine, and the Android IPC Layer. Each subsystem communicates through well-defined interfaces, enabling modularity and testability.

The Command Dispatcher acts as the central router, receiving input from the CLI, piped streams, or the daemon. It resolves the appropriate handler and delegates execution downstream. The Provider Bridge normalizes responses from heterogeneous AI providers into a unified internal format.

info
Design principle: Every subsystem boundary uses a trait-based interface (Rust) or protocol buffer (Python) so that internal implementations can be swapped without touching the rest of the codebase.

02

The 4-Stage Execution Pipeline

Every command processed by PHOENIX flows through a four-stage pipeline. Each stage performs a discrete transformation and enforces specific safety checks before passing control to the next.

STAGE 1

Input Parsing & Normalization

Raw input (CLI args, piped stdin, daemon request) is tokenized, validated, and normalized into a structured CommandRequest object. The parser handles shell quoting, variable expansion, and heredoc syntax.

let request = CommandRequest::parse("phoenix code --diff ./src")?;
STAGE 2

Context Assembly & Provider Routing

The system assembles relevant context from the local memory store, file tree scanner, and session history. The provider router selects the optimal AI backend based on latency, cost, and capability requirements.

let context = memory.build_context(&request, 2048); let provider = router.select(request.model_hint);
STAGE 3

Safety Inspection & Sandboxed Execution

Commands are scanned for destructive patterns (rm -rf, fork bombs, credential exposure). Approved commands execute inside a bubblewrap or nsjail sandbox with network isolation, memory limits, and filesystem whitelisting.

let verdict = safety.inspect(&command); if verdict.is_dangerous() { return Err(SandboxDenied); }
STAGE 4

Output Streaming & Telemetry Logging

Execution results are streamed back via PTY to the terminal or daemon. Each stage's latency, token usage, and error counts are logged to the embedded telemetry store for the daemon dashboard.

let output = sandbox.execute(command).await?; telemetry.record(StageResult::new(output));
speed
Performance target: End-to-end pipeline latency under 24ms for local commands, under 200ms for API-routed completions (OpenRouter, Groq). Telemetry is recorded asynchronously to avoid impacting pipeline throughput.
03

Termux & Android IPC Bridge Internals

The Android IPC bridge enables PHOENIX to interact with device hardware, sensors, and system services from within the Termux sandbox. It uses a combination of Termux API FFI bindings, ADB proxying, and direct Android intent dispatch.

IPC Message Protocol

The bridge uses a length-prefixed binary protocol over Unix domain sockets. Messages are serialized with bincode and include a magic byte, message type, sequence number, and payload. The Rust implementation handles both the server (Termux side) and client (Python agent side) roles.

code ipc_bridge.rs Rust 
use tokio::net::UnixStream;
use serde::{Serialize, Deserialize};

#[derive(Serialize, Deserialize)]
pub struct IpcMessage {
    magic: [u8; 4],        // b"PHNX"
    msg_type: MessageType,
    seq: u32,
    payload: Vec<u8>,
}

#[derive(Serialize, Deserialize)]
pub enum MessageType {
    TermuxApi,
    AdbCommand,
    SensorRead,
    IntentDispatch,
    Heartbeat,
}

pub async fn send_request(
    stream: &mut UnixStream,
    msg: IpcMessage,
) -> Result<IpcMessage> {
    let encoded = bincode::serialize(&msg)?;
    stream.write_all(&(encoded.len() as u32).to_le_bytes()).await?;
    stream.write_all(&encoded).await?;

    let mut len_buf = [0u8; 4];
    stream.read_exact(&mut len_buf).await?;
    let resp_len = u32::from_le_bytes(len_buf) as usize;
    let mut resp_buf = vec![0u8; resp_len];
    stream.read_exact(&mut resp_buf).await?;
    Ok(bincode::deserialize(&resp_buf)?)
}

Supported IPC Operations

phone_android Termux API

WiFi control, battery status, clipboard, camera, contacts, notifications, sensors, and SMS via the Termux:API addon.

usb ADB Proxy

Remote shell execution, file push/pull, screenshot capture, input injection, and logcat streaming over USB/WiFi.

send Intent Dispatch

Fire Android intents for deep linking, app launching, and inter-app communication via am start commands.

sensors Sensor Access

Accelerometer, gyroscope, GPS location, and ambient light sensor data for environmental awareness.

warning
Security note: The IPC bridge enforces a strict message validation layer. All incoming messages are checked for valid magic bytes, sequence ordering, and payload size limits (max 1MB). Invalid messages are logged and the connection is terminated immediately.
04

Process Isolation & Safety Boundaries

PHOENIX enforces strict process isolation to prevent AI-generated commands from damaging the host system. The execution engine uses Linux namespaces and seccomp filters to create a sandboxed environment with limited system call access.

Safety Boundary Architecture

The safety model operates on three concentric rings. The innermost ring is the Provider Bridge, which has no direct access to the filesystem or process table. The middle ring is the Execution Engine, which operates with constrained privileges inside a sandbox. The outermost ring is the Core Runtime, which has full host access but delegates all dangerous operations inward.

R1
Ring 1 — Provider Bridge (Untrusted)

Receives API responses, parses JSON, validates schema. No system access. Runs in a Tokio task with a 10-second timeout.

R2
Ring 2 — Execution Engine (Sandboxed)

Runs shell commands inside bubblewrap with restricted syscalls. Filesystem is read-only except /tmp. Network disabled in safe mode.

R3
Ring 3 — Core Runtime (Host)

Manages sessions, config, and telemetry. The only ring with full host access. All dangerous operations are delegated to Ring 2.

verified
Verified: Safety boundaries are tested against a comprehensive attack matrix including fork bombs, credential exfiltration, network tunneling, and symlink traversal. All tests run in CI on every commit.
